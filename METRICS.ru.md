# Статистика одной задачи

Когда агент сообщает «готово», из этого ещё не видно, сколько раз он исправлял код и чем закончились тесты. `kit/task_metrics.py` собирает эти сведения и расход токенов в один отчёт. Его можно прочитать в итоговом ответе или открыть позже в папке задачи.

В обычной работе команды вызывает билдер — основной агент `build`. Ниже они показаны, чтобы ты мог понять процесс, проверить его вручную или найти причину пропавших данных. Скрипт работает на Python без дополнительных пакетов. Он выполняется только при вызове, поэтому пропущенные билдером события сам не восстановит.

Проверенная интеграция: **OpenCode CLI 2.0.21**. Дата проверки: **03.10.2026**. Экспорт и API списка потомков проверены на установленном CLI. Суммы входа, выхода и рассуждений сверены со 191 сообщением существующей сессии. Дочерних сессий в ней не было: обход потомков и страниц проверен автоматическими тестами. Счётчики ревью и тестов работают без OpenCode; для токенов нужен доступ к его сессиям.

## Как пользоваться в обычной задаче

Ты описываешь задачу Мастер Чифу и согласовываешь план. Дальше он сам открывает учёт, управляет исполнителями, записывает результаты ревью, запускает тесты и получает отчёт. В итоговом ответе ты видишь две группы токенов, число переделок и результаты проверок. Эти обязанности записаны в `AGENTS.md`.

Команды `start`, `review`, `test` и `finish` нужны Мастер Чифу для выполнения этих действий. Выполнять их вручную при каждой задаче пользователю не требуется.

## Техническая справка и ручная отладка

Остальная часть документа предназначена для проверки и изменения самого скрипта. Например, она поможет повторить вызов, если Мастер Чиф получил ошибку. Примеры ниже показывают инструменты агента, а не обязательные действия пользователя.

### Что делает каждая команда

Учёт проходит вместе с задачей: сначала нужно отметить начало, затем записывать проверки, а в конце собрать результат. Для каждого из этих действий есть своя команда.

| Команда | Действие |
|---|---|
| `start` | Создаёт задачу и фиксирует время начала |
| `review` | Записывает результат одного ревью |
| `check` | Пробный запуск тестов без задачи: проверяет, что скрипт может прочитать их результат |
| `test` | Запускает тесты и записывает результат |
| `resume` | Снимает остановку по защитному лимиту после решения пользователя |
| `finish` | Получает токены, закрывает задачу и печатает отчёт |

Для ручной проверки открой терминал в папке с `opencode.jsonc` и `kit/` — это корень проекта. В примере ниже задача называется `expenses-001`, а проверяемый класс — `ExpenseService`. `ses_...` — место для настоящего ID разговора в OpenCode, оставлять эти точки в команде нельзя. Пример показывает код, который сначала вернули на исправление, а после повторного ревью приняли. При реальной работе записывай только те ревью, которые действительно были.

```powershell
py kit/task_metrics.py start --task expenses-001 --session ses_... --title "Учёт расходов"
py kit/task_metrics.py review --task expenses-001 --piece ExpenseService --result rework
py kit/task_metrics.py review --task expenses-001 --piece ExpenseService --result accepted
py kit/task_metrics.py test --task expenses-001 -- py -m unittest discover -s kit/tests -v
py kit/task_metrics.py finish --task expenses-001
```

Команды написаны для Windows. На macOS и Linux вместо `py` пишите `python3`.

Для запуска из другой папки укажите `--root <папка проекта>` **перед** командой `start`, `test` и т. д.

## 1. Начало и границы задачи

В одном чате можно выполнить несколько задач. Чтобы не приписать новой задаче все прошлые токены, скрипту нужны отдельное имя и время начала. Их и записывает `start`.

`start` создаёт `.metrics/expenses-001/events.jsonl`. JSONL — текстовый файл, где каждое событие записано отдельной JSON-строкой. Скрипт сохраняет время, название задачи и ID сессии.

ID сессии берётся из контекста OpenCode. Если он неизвестен, билдер может проверить `opencode session list --format json`, но не должен автоматически выбирать последнюю сессию: она может относиться к другой задаче. Можно начать без `--session`; тогда токены будут отмечены как недоступные.

Время задачи — от `start` до `finish`, включая ожидание пользователя. Это не чистое время работы модели. Не ведите одновременно две учитываемые задачи в одной сессии: их интервалы пересекутся.

## 2. Ревью и переделки

Ревью — это проверка написанного кода. Например, билдер заметил, что функция принимает отрицательную сумму расхода, и попросил исполнителя исправить её. Такой возврат должен попасть в статистику, даже если следующий запуск тестов уже прошёл.

Билдер записывает решение через `review`:

- `accepted` — проверенный фрагмент принят;
- `rework` — фрагмент возвращён на исправление.

Три замечания в одном возврате дают одну переделку. Первое написание кода не считается переделкой. Скрипт не анализирует текст переписки и не угадывает причину изменения кода. Пропущенная команда `review` означает пропущенную запись в статистике.

## 3. Прогоны тестов

Чтобы не полагаться на слова агента «тесты прошли», скрипт запускает их сам. Билдер передаёт ему ту команду, которой обычно проверяется проект. Один такой запуск всего набора называется прогоном.

`test` запускает команду после `--` и сохраняет её вывод в `.metrics/<ID>/test-<номер>.log`. По умолчанию лимит времени — 300 секунд; его можно изменить через `--timeout 600`.

Полностью успешный прогон означает: команда завершилась с кодом 0, тестов больше нуля, нет падений, ошибок, пропусков или ожидаемых неудач. «3 из 5» означает три успешных запуска из пяти, а не три отдельных теста.

У тестовых инструментов разные форматы результатов. Скрипт должен распознать число тестов и ошибок, прежде чем считать прогон успешным. Сейчас он понимает:

- стандартный итог Python `unittest`;
- один файл JUnit XML через `--junit <путь>` для других инструментов.

JUnit XML — файл с результатами тестов в согласованном формате. Его умеют создавать разные инструменты, не только Java. Например, если в твоём проекте уже используется pytest, можно попросить его создать такой файл и передать путь скрипту:

```powershell
py kit/task_metrics.py test --task expenses-001 --junit .metrics/expenses-001/run-01.xml -- py -m pytest --junitxml=.metrics/expenses-001/run-01.xml
```

Файл XML не должен существовать до запуска: так скрипт не примет старый отчёт за новый. Для следующего прогона используйте другое имя.

Maven и Gradle пишут не один файл, а отдельный файл на каждый тестовый класс. Для них есть `--junit-dir <папка>`: скрипт читает все XML-файлы в папке, но **только записанные во время этого прогона**. Файлы от прошлых запусков пропускаются по времени изменения. Папка может существовать заранее.

```powershell
py kit/task_metrics.py test --task expenses-001 --junit-dir target/surefire-reports -- mvn -q test
```

Если хотя бы один файл из прогона повреждён, результат считается неизвестным: неполная сумма выглядела бы как меньший, но полный набор тестов.

На Windows скрипт сам находит программы, которые запускаются через `.cmd` или `.bat`: `mvn`, `npx`, `npm`, `gradlew`. Писать `mvn.cmd` не нужно.

Если формат вывода неизвестен, результат будет `unknown`, даже при коде выхода 0. Пустой набор — `empty`, пропуски — `skipped`, превышение времени — `timeout`. Эти исходы не увеличивают число полностью успешных прогонов. Команда оболочки с `&&` или `|` не разбирается: передавайте исполняемый файл и аргументы.

### Что значит прогон для работы Мастер Чифа

Кроме статуса, каждый прогон получает **категорию**. Она отвечает на главный вопрос: запустились ли тесты вообще. От этого зависит, кто должен исправлять проблему.

| Категория | Когда | Кто исправляет | Код выхода `test` |
|---|---|---|---|
| `passed` | тесты прошли, все зелёные | никто | 0 |
| `tests_failed` | тесты запустились, часть упала | исполнитель (переделка) или Мастер Чиф, если неверен сам тест | 1 |
| `incomplete` | тесты запустились без падений, но часть пропущена | Мастер Чиф разбирается, почему пропущены | 1 |
| `no_result` | результата нет: проект не собрался, нет программы, неверная команда, не найден логгер, ноль тестов | Мастер Чиф чинит настройку или спрашивает пользователя; исполнитель — только если ошибка компиляции в его свежем коде | 4 |
| `timeout` | команда не завершилась за отведённое время | Мастер Чиф или пользователь: часто это режим наблюдения у Jest/Vitest | 4 |

Для `no_result` и `timeout` скрипт добавляет в событие поле `hints` — подсказки по типичным причинам: не найден логгер `dotnet test`, ошибка компиляции, режим наблюдения, отсутствующий отчёт, нераспознанный формат.

### Пробный запуск: `check`

`check` запускает команду тестов без задачи и без журнала. Он отвечает на один вопрос: сможет ли `test` прочитать результат.

```powershell
py kit/task_metrics.py check --junit-dir target/surefire-reports -- mvn -q test
```

- Код выхода 0 и строка `CHECK OK` — настройка в порядке. Упавшие тесты здесь не мешают: важно, что результат читается.
- Код выхода 4 и `CHECK FAILED` — результат не читается. Ниже напечатаны подсказки.

Если указан `--junit <файл>`, `check` после чтения удаляет этот файл, чтобы то же имя можно было использовать снова. Мастер Чиф вызывает `check` один раз перед каждой задачей с кодом. Пользователю стоит запустить его сам при подключении кита к новому проекту.

## 3а. Защита от зацикливания

Если проект не собирается или задание противоречит тестам, Мастер Чиф может бесконечно гонять тесты и возвращать код исполнителю. Скрипт ограничивает это сам, по журналу, а не по обещаниям агента.

| Лимит | По умолчанию | Что считает |
|---|---|---|
| `max_reworks` | 3 | возвраты одного и того же куска кода исполнителю |
| `max_no_result` | 3 | прогоны подряд без читаемого результата (`no_result`, `timeout`) |
| `max_failed_runs` | 12 | неуспешные рабочие прогоны подряд в одной области тестов; начальный baseline не входит |
| `max_runs` | 60 | все прогоны после start/resume, включая baseline и проверки отдельных классов |

Как это работает:

1. После каждого `review` и `test` скрипт проверяет журнал. Если лимит достигнут, он дописывает событие `halt` с причиной и возвращает код выхода **3**. В поток ошибок печатается строка `STOP:` и указание остановиться.
2. Пока задача остановлена, `review` и `test` отказываются работать и тоже возвращают 3. `finish` работает: отчёт можно получить.
3. Продолжить можно только командой `resume` с причиной — решением пользователя. Причина попадает в журнал и в отчёт. После `resume` все счётчики начинаются с нуля.

```powershell
py kit/task_metrics.py resume --task expenses-001 --reason "Пользователь уточнил задание: скидка больше 100% — ошибка"
```

Лимиты задаются при `start`, если нужны другие: `--max-reworks 5 --max-runs 120`. Значения хранятся в событии `start`. Старые журналы без лимитов используют значения по умолчанию.

Ограничение честное: скрипт не управляет агентом. Он надёжно фиксирует остановку и отказывается записывать новые прогоны, а правило «на коде 3 остановиться и спросить пользователя» записано в `AGENTS.md`. Если агент нарушит правило и продолжит работу без утилиты, в отчёте не будет новых прогонов, и это будет видно.

### Коды выхода

| Код | Значение |
|---|---|
| 0 | команда выполнена; для `test` — прогон `passed`; для `check` — результат читается |
| 1 | `test`: тесты запустились, но не все зелёные |
| 2 | ошибка вызова или повреждённый журнал |
| 3 | STOP: достигнут защитный лимит или задача уже остановлена |
| 4 | `test` или `check`: тесты не дали читаемого результата |

## 4. Получение токенов

Число токенов не нужно просить у модели: OpenCode уже сохраняет его рядом с ответами. `finish` читает эти записи. Разговоры исполнителей хранятся в отдельных дочерних сессиях, поэтому недостаточно прочитать только основной чат.

Вот что происходит при сборе:

1. Запоминает время окончания до обращения к OpenCode.
2. Выполняет `opencode session export <ID>` и читает JSON в памяти. Для старого CLI предусмотрена попытка `opencode export <ID>`.
3. Находит дочерние сессии через `opencode api session.list --param parentID=<ID> --param limit=100`, включая следующие страницы. Повторяет поиск для каждого потомка. Дополнительно проверяет ID дочерних сессий в метаданных инструментов.
4. Принимает только основную сессию и её потомков по `parentID`.
5. Берёт завершённые сообщения `assistant`, созданные после `start` и завершённые не позднее `finish`. Повторы с одинаковыми ID не суммируются дважды.
6. Группирует счётчики по провайдеру и модели. Переписку и исходный экспорт на диск не сохраняет.

В экспорте **2.0.21** верхний уровень содержит `info` и `messages`. Сообщение имеет `type: assistant`, `model.providerID`, `model.id`, `time.created`, `time.completed` и `tokens`. Время хранится в миллисекундах. Читаются `tokens.input`, `output`, `reasoning`, `cache.read`, `cache.write`. Старый вариант с `messages[].info` тоже поддержан тестами.

Итоговые счётчики `info.tokens` всей сессии не используются: туда входит работа до текущей задачи. Токены из сообщений и частей `step-finish` не складываются вместе, иначе получится двойной счёт.

Все модели с провайдером **`lmstudio`** относятся к бесплатной/локальной группе. Любой другой известный провайдер — к платной. Неизвестный провайдер показан отдельно. «Локальная» означает отсутствие платы за API; расход электричества не измеряется.

Вход, выход, рассуждения и кэш показаны отдельно. Скрипт не складывает их в один показатель: у разных провайдеров эти категории могут пересекаться. Отсутствующий счётчик показан как «нет данных», а не 0.

## 5. Итоговый отчёт

Отчёт нужен, чтобы в конце задачи ты увидел результат в одном месте и мог вернуться к нему позже. Числа уже подсчитаны скриптом; агенту остаётся показать их в ответе.

`finish` сохраняет `.metrics/<ID>/report.md` и печатает его в терминал. Билдер добавляет этот блок в ответ пользователю. Если ответ пишет планировщик, он читает тот же файл; повторный сбор не нужен.

В отчёте есть длительность, две группы моделей, токены, число ревью и возвратов, число успешных прогонов и результат последнего запуска. Если были прогоны без результата, отчёт показывает их отдельно и отмечает, что это не ошибки исполнителя. Если срабатывали защитные лимиты, отчёт перечисляет остановки и решения пользователя, после которых работа продолжилась. Данные относятся только к записанным событиям. Отчёт не заменяет приёмку задачи.

Повторный `finish` возвращает прежний результат. После закрытия нельзя добавлять ревью и тесты: для новой работы создайте новый ID. Если сбор токенов завершился ошибкой, задача всё равно закрывается с предупреждением — счётчики тестов и ревью сохраняются. Исходные экспорты можно отдельно проверить через Python API `parse_exports`; закрытый отчёт не меняет границы задним числом.

Срез не включает финальный ответ после `finish`, незавершённые сообщения и служебные запросы, которых нет в экспорте. Запрос, начатый до `start`, тоже не включается. Скрипт не вычисляет стоимость или экономию.

## Если CLI не найден

CLI — OpenCode, вызываемый из терминала. Если скрипт не может его запустить, он не получит сохранённые сообщения и токены. Это не мешает записывать ревью и тесты: для них хватает Python.

На Windows скрипт сначала проверяет встроенный CLI Desktop в `%LOCALAPPDATA%\Programs\@opencodedesktop\resources\opencode-cli.exe`, затем команду `opencode` в `PATH`. Можно указать путь явно:

```powershell
py kit/task_metrics.py finish --task expenses-001 --opencode "C:\путь\opencode-cli.exe"
```

Также можно передать готовые выгрузки: `finish --task expenses-001 --export root.json --export child.json`. Укажите основную сессию и всех нужных потомков. Такие файлы создавайте штатным экспортом, не придумывайте значения токенов. Экспорт может содержать переписку, поэтому храните его локально.

## После обновления OpenCode

Разработчики OpenCode могут изменить команды или структуру данных. Наш код продолжит запускаться, но перестанет находить нужные поля. Следующие шаги помогут отличить проблему подключения от изменения формата и понять, что именно нужно исправить.

1. Посмотрите версию: `opencode --version`. Убедитесь, что CLI видит нужные сессии и подключён к тому же серверу, что Desktop.
2. Проверьте справку `opencode session export --help` и наличие команды `opencode api`.
3. Запустите `py -m unittest discover -s kit/tests -v`.
4. Проведите небольшую новую задачу с одним исполнителем и одним запуском тестов. Сверьте обе группы токенов с экспортами основной и дочерней сессий.
5. При изменении JSON сначала поправьте `message_info`, `parse_exports` или `collect_exports`, затем добавьте тест с обезличенным примером нового формата.
6. Только после этой проверки укажите новую проверенную версию в README и здесь. Пока данных нет, оставляйте предупреждение; не заменяйте его нулями.

Документация OpenCode: [команды CLI](https://opencode.ai/v2/docs/cli/commands/), [API сессий](https://opencode.ai/v2/docs/api).

## Хранение

Журнал помогает проверить происхождение числа в отчёте. Например, если в нём два неуспешных прогона, можно открыть сохранённый вывод этих запусков и посмотреть ошибки.

Папка `.metrics/` исключена из Git. В ней остаются журнал, агрегированные токены, отчёт и вывод тестов. В выводе тестов могут быть данные приложения. Один процесс записывает одну задачу; одновременная запись блокируется файлом `.lock`. Если процесс аварийно завершился, сначала проверьте, что он больше не работает, и только затем удаляйте оставшийся `.lock`.

## Учёт заданий и проверка границ

Для новых задач с исполнителем Мастер Чиф добавляет `--track-delegations` к start и регистрирует каждый вызов через delegate. Задание получает ID, список разрешённых файлов, область тестов и список требований. Пропущенное ревью теперь видно в отчёте; без регистрации задания скрипт не позволит записать ревью в таком режиме. Старые журналы и команды без этого режима остаются читаемыми.

Перед приёмкой нужно заполнить проверку каждого требования, запустить подходящие тесты и вызвать review с `--checks`. Пример полного протокола — [PIPELINE.ru.md](PIPELINE.ru.md). Скрипт проверяет состав доказательств и границы файлов, но не понимает смысл программы вместо ревьюера.

Команда test принимает `--scope <класс-или-модуль>`; без него область называется full. Фильтр тестов задаётся в команде самого тестового инструмента: один scope не фильтрует тесты автоматически. Начальную проверку заглушек можно один раз до реализации записать с `--phase baseline`; повторять её в той же области или включать после рабочих прогонов нельзя. Не называйте каждый повтор новым scope ради обхода лимита.

Число зелёных прогонов включает и отдельные модули. Отчёт отдельно показывает прогоны full; готовность всей задачи требует последнего зелёного полного прогона. Ни baseline, ни пустой/нечитаемый результат не превращаются в успешную проверку.

Мастер Чиф запускает start до подготовки окружения, как только получил настоящий ID сессии. Поэтому время подготовки после start входит в длительность. Сам скрипт не узнает о работе до start и о вызовах, сделанных без регистрации; эти ограничения прямо написаны в отчёте.

Если после зелёного прогона изменились файлы проекта, принятие блокируется до повторного запуска тестов. Это относится и к новым тестам, которые Мастер Чиф добавил при ревью. Служебные файлы в .metrics/ не требуют нового прогона.
