# Как Мастер Чиф проверяет работу исполнителя

Пользователь описывает задачу и согласовывает план. Команды ниже выполняет Мастер Чиф; они показаны здесь для понимания и отладки.

## Что было не так с первым ревью

В игре требовалось: если ID игры равен null, вернуть понятную ошибку «Игра не найдена». Исполнитель написал:

```java
Game game = games.get(id);
if (id == null || game == null) {
    throw new GameNotFoundException("Игра не найдена");
}
```

Но ConcurrentHashMap не принимает null. Программа падает уже на первой строке и не доходит до проверки. Проверять нужно до обращения к карте:

```java
if (id == null) {
    throw new GameNotFoundException("Игра не найдена");
}
Game game = games.get(id);
```

Мастер Чиф принял первый вариант: имеющиеся тесты не передавали null. Дополнительный тест нашёл ошибку. Поэтому «тесты зелёные» недостаточно: нужно ещё проверить, что тесты охватывают требования.

Теперь Мастер Чиф до вызова исполнителя сохраняет отдельный список требований, включая null, порядок проверок и состояние после отклонённого хода. После ответа для каждого пункта записывает место в коде и проверяющий тест. Если какой-то пункт не проверен, скрипт не принимает результат. Это не математическое доказательство правильности: Мастер Чиф всё ещё может ошибиться при чтении кода или составлении исходного списка.

## Почему задание стало крупнее

Раньше допускался вызов исполнителя ради одного короткого метода. На реальном прогоне даже конструкторы проходили отдельные вызовы и полный набор тестов.

Теперь обычное задание — небольшой класс целиком, с конструктором и связанными методами. Например, весь GameService за один вызов. Большой класс Мастер Чиф разделит, но должен объяснить границы. Точечное исправление одной функции тоже допустимо. Весь проект или модуль из нескольких файлов одному исполнителю не отдаётся.

## Что защищает чужие файлы

До вызова исполнителя `delegate` делает снимок содержимого файлов проекта. Сразу после ответа `inspect` сравнивает новый снимок с исходным: видит изменения, удаления и новые файлы. Наличие коммита или отслеживания Git не требуется; `.gitignore` исходные файлы не скрывает.

Разрешён только переданный файл. Если исполнитель изменил тесты или другой исходник, принятие блокируется. Мастер Чиф фиксирует возврат, разбирает посторонние изменения, восстанавливает только их и регистрирует новую попытку. Скрипт сам ничего не удаляет и не откатывает. Снимок inspect нельзя перезаписать. Мастер Чиф делает его до собственных изменений; затем может дописать недостающие тесты, и эти правки записываются отдельно. Менять реализацию проверяемого файла после inspect нельзя: нужна новая попытка. Если после зелёного прогона Мастер Чиф добавил тест или изменил другой файл проекта, скрипт требует запустить тесты снова. Старый результат не подтверждает новую версию файлов.

Снимок пропускает служебные и сгенерированные папки: `.git`, `.metrics`, `__pycache__`, `.venv`, `node_modules`, `target`, `build`, `dist`, `bin`, `obj`. Исходники в этих папках хранить нельзя. Логи, отчёты и таблицы ревью нужно писать в `.metrics/`, чтобы они не выглядели как посторонние изменения. Символические ссылки и junction вне исключённых папок останавливают проверку.

## Нужно ли увеличивать лимит тестов

В первом прогоне Мастер Чиф запускал весь набор, хотя следующие модули ещё состояли из заглушек. Эти тесты ожидаемо падали и приближали остановку по лимиту. Увеличить число можно, но тогда скрипт дольше терпел бы и настоящую повторяющуюся ошибку.

Теперь Мастер Чиф проверяет текущий класс или модуль подходящим фильтром тестового инструмента. Например, Maven может запускать только GameServiceTest. Область записывается как `--scope GameService`; сам scope не фильтрует тесты.

Начальный красный прогон до реализации записывается один раз с `--phase baseline`. Он сохраняется в журнале, но не расходует лимит неуспешных рабочих прогонов. Повторить baseline или включить его после начала работы в той же области нельзя. Ошибка сборки, отсутствие результата и тайм-аут по-прежнему учитываются: заглушки не оправдывают сломанное окружение.

Лимит 12 теперь относится к последовательным рабочим неуспешным прогонам одной области. Падения разных модулей не складываются. Полный зелёный прогон сбрасывает все такие серии. Общий лимит 60 запусков остаётся, как и лимиты повторных возвратов и отсутствия результата. Менять названия областей ради обхода остановки запрещено.

Перед завершением задачи Мастер Чиф обязательно запускает весь набор без фильтра с `--scope full`. Зелёный тест одного класса не означает, что весь проект готов.

## Как записываются ревью и время

Скрипт сам запускает тесты, читает их результат и записывает счётчик. Но решение «код принят» или «вернуть на доработку» принимает Мастер Чиф; для этого он вызывает review.

Теперь перед каждым вызовом модели Мастер Чиф регистрирует задание. Если задание есть, а ревью забыто, отчёт покажет его как незавершённое. В режиме `--track-delegations` записать ревью без зарегистрированного задания нельзя. Это контроль нашего протокола, а не перехват всех действий OpenCode: если агент обойдёт и delegate, и review, скрипт о таком вызове сам не узнает.

Время считается между start и finish. Раньше настройка Java и запуск LM Studio прошли до start и в 29 минут не вошли. Теперь инструкция требует start сразу после получения настоящего ID сессии, до настройки окружения и дальнейшей работы. То, что случилось до start, задним числом не добавляется.

## Пример одного задания

Сначала Мастер Чиф начинает учёт всей задачи:

```powershell
py kit/task_metrics.py start --task game-001 --session <реальный-ID> --track-delegations --title "Крестики-нолики"
```

Пишет `.metrics/game-001/GameService-requirements.json`:

```json
[
  "null проверяется до обращения к карте",
  "неизвестный ID вызывает GameNotFoundException"
]
```

После каркаса и тестов регистрирует задание, затем вызывает executor:

```powershell
py kit/task_metrics.py delegate --task game-001 --work-item GameService --scope GameService --files src/main/java/example/GameService.java --requirements .metrics/game-001/GameService-requirements.json
```

Сразу после ответа фиксирует изменения, до своих правок и запуска тестов:

```powershell
py kit/task_metrics.py inspect --task game-001 --work-item GameService
```

Код выхода 1 означает посторонние изменения: нужно записать rework и разобраться с ними. Если границы соблюдены, Мастер Чиф читает код, проверяет требования, добавляет недостающие тесты и запускает их:

```powershell
py kit/task_metrics.py test --task game-001 --scope GameService --junit-dir target/surefire-reports -- mvn -q -Dtest=GameServiceTest test
```

Сохраняет `.metrics/game-001/GameService-checks.json`. Текст каждого requirement должен совпадать с исходным списком:

```json
[
  {
    "requirement": "null проверяется до обращения к карте",
    "code": "GameService.java:getGame, проверка перед games.get",
    "test": "GameServiceTest.nullIdIsRejected",
    "verified": true
  },
  {
    "requirement": "неизвестный ID вызывает GameNotFoundException",
    "code": "GameService.java:getGame, проверка game == null",
    "test": "GameServiceTest.unknownIdIsRejected",
    "verified": true
  }
]
```

Принимает результат:

```powershell
py kit/task_metrics.py review --task game-001 --work-item GameService --result accepted --checks .metrics/game-001/GameService-checks.json
```

При ошибке вместо принятия фиксирует `review --result rework`, исправляет спецификацию или возвращает замечания исполнителю. Перед повторным вызовом снова запускает delegate. Когда все модули готовы, запускает полный набор с `--scope full` и только после этого finish.
